## 本次新增解析（2 篇，均为历史缺口）

### 1. AgentHPOBench: A Benchmark For Evaluating LLM Agents as Sequential Hyperparameter Optimizers

- 来源：[arXiv:2607.29626v1](https://arxiv.org/abs/2607.29626)、[作者代码](https://github.com/OpenMOSS/AgentHPOBench)；当前核验为 2026 arXiv 预印本。
- 收录原因：30 个真实 ML 仓库、共享 baseline 与五次顺序干预，为“Agent 是否利用实验反馈”提供可执行 benchmark、typed validation 和完整 trace 设计。
- 主要证据：limited-budget 主表中 Claude Sonnet 4.6 的 MBNS/BWR/MAA 为 `0.407/76.7%/79.5%`；Qwen3-32B 的 standard/no-feedback MBNS 为 `0.148/0.052`。开源方法和经典基线有三 seeds，API Agent 只有一次 audited run。
- 分类修正：公开 commit `6d8d900…` 的 30 个 task 中，本轮静态审计发现至少 11 个会改变 `d_model`、layers、heads、model/architecture family 等结构字段，故归入 `mixed-search-space`，不能作为固定架构 HPO 总体证据。
- 关键限制：部分循环直接观察 test 类指标；主表用 final-step，改用 best-so-far 后 random/TPE/BOHB-style MBNS 升至 `0.325/0.298/0.291`，超过所有开源 Agent。代码未提交 raw runs/生成 summaries，论文也未给总 GPU-hours、wall time 或统一货币成本。
- 与当前方向：复用 baseline + 五步 typed intervention + provenance/no-feedback；必须拆分 architecture-only/HPO-only/mixed，反馈 validation-only，并同时报告 final 与 incumbent。

### 2. When Is an LLM Worth It for Hyperparameter Optimization?

- 来源：[arXiv:2606.21641v2](https://arxiv.org/abs/2606.21641)、[HTML](https://arxiv.org/html/2606.21641v2)；当前核验为 2026 arXiv 预印本。
- 收录原因：直接回答 LLM HPO 的 early advantage 是否来自模型，提供 default-seeded random 的精确对照、matched evaluation curves、5 seeds 与 paired/bootstrap 统计。
- 主要证据：LLM-OptFlow 的第一次 evaluation 是 LLM 调用前的 fixed random-forest default，mean best-CV `88.7%`；LLM proposals 在 12 evaluations 相对 default 只增加 `+0.40 pp` CV，held-out test 为 `-0.01 pp`、`p=0.92`。给 random 同一 default 后，LLM 在 5 次无优势，12 次落后 `-0.37 pp`。
- 分类修正：空间跨 logistic regression、random forest、gradient boosting、SVC 四种模型族及其参数，因此归入 `mixed-search-space`，不是固定架构 HPO。
- 关键限制：模型差异主要由单个 `vehicle` 任务驱动；TPE/GP 的前 10 次是 random startup；论文声称释放 harness/`significance.py`，但 arXiv 未给代码 URL，GitHub repository search 也未找到项目，完整复现证据不足。
- 与当前方向：任何 AgenticNAS warm-start 都必须把 evaluation 0/default 与 Agent proposal 分开，并给 random/evolution/BO 相同初始架构与相同候选/训练预算。

## 已筛选、暂不入库

- [Do AI Agents Understand Computer Architecture?](https://arxiv.org/abs/2609.19387) 在 15 维 accelerator space 中测试 Agent 是否理解硬件语义；搜索对象是计算机体系结构旋钮，不是真实神经网络架构，因此只作为“语义理解 vs 黑箱搜索”邻接方法。
- [Layer-wise Curriculum Learning for Efficient LLM Compression](https://arxiv.org/abs/2609.19213) 固定压缩/蒸馏流程并做层段课程学习，没有 LLM Agent proposal loop 或神经架构搜索对象。
- [Evolution or Illusion?](https://arxiv.org/abs/2609.19799) 的 seeds × iterations 结论继续作为预算报告协议参考，但它搜索程序而非神经架构；[Portfolio-Based CMOBO](https://arxiv.org/abs/2609.19550) 搜索材料实验决策，仍不入 NAS/HPO 索引。
- 本轮仍未发现直接针对 4–10 层 Conv1d Transformer、同时把真实 latency、peak memory 或 energy 纳入 LLM Agent 闭环的新论文。

## 重点结论与后续问题

- **先审计搜索变量，再贴 HPO/NAS 标签。** “任务名叫 HPO”不代表架构固定；`d_model`、heads、layers、model family 等字段必须把任务转入 mixed lane。
- **default 必须单独计账。** LLM 调用前的 baseline/evaluation 0 不能记作 Agent warm-start；经典搜索也必须获得同一初始点。
- **最终口径至少双报。** final-step 测持续改进/保留能力，best-so-far 测发现能力；两者会改变方法排名，不能互相替代。
- **反馈必须 validation-only。** benchmark 的 test-visible objective 适合测操作能力，不适合声称泛化；最终 test 只能在选定 incumbent 上一次确认。
- **成本仍未闭合。** 候选数相同不等于成本相同；下一步需统一 request/retry/token、GPU-hours、wall time、失败候选和真实设备 latency/memory/energy。
- **下一轮优先级。** 检查下一次 arXiv 公告；寻找 AgentHPOBench 的 architecture-only 子集与 raw runs；继续追踪预算匹配论文的代码链接；保持 Conv1d Transformer 与真实设备 Pareto 搜索为首要缺口。
